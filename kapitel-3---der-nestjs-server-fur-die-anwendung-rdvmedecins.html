    • Zeilen 20–24: [DROP TABLE IF EXISTS …] – das Skript beginnt bei jeder Ausführung mit einer leeren Datenbank, in umgekehrter Reihenfolge der Abhängigkeiten (beginnend mit `appointments`, das auf `[slots]` und `clients` verweist, bis hinunter zu `users`, auf das niemand verweist): [MySQL] würde sich weigern, eine Tabelle zu löschen, auf die noch ein Fremdschlüssel verweist;
    • Zeile 48: [doctor_id INT NOT NULL], dann Zeile 53: [CONSTRAINT fk_slots_doctor FOREIGN KEY …] – ein Zeitfenster gehört immer zu einem Arzt;
    • Zeile 64: [CONSTRAINT unq1_appointments UNIQUE (day, slot_id)] – die zentrale Geschäftsregel der Anwendung: Dasselbe Zeitfenster am selben Tag kann nur einmal gebucht werden. Diese Bedingung, und nur sie, verhindert einen doppelten Termin – weder der Validator noch die Geschäftslogik prüfen sie ausdrücklich erneut (siehe unten, addAppointment);
    • Zeilen 67–74: [CREATE TABLE users (…)] – die in diesem Schritt hinzugefügte Tabelle. `login` ist UNIQUE (zwei Benutzer können nicht dieselbe Anmeldekennung haben); `password` speichert ein mit bcrypt gehashtes Passwort (niemals im Klartext); role ist entweder 'ADMIN' oder 'USER' – eine einfache Textspalte, während das ursprüngliche Dokument drei Tabellen verwendete (users, roles, users_roles), um mehrere Rollen pro Benutzer zu ermöglichen. Da diese Anwendung nur zwei sich gegenseitig ausschließende Rollen benötigt, wäre die ursprüngliche Many-to-many-Beziehung überdimensioniert gewesen;
    • Zeilen 91–93: [INSERT INTO users …] – zwei Demokonten, admin/admin (Rolle ADMIN) und user/user (Rolle USER), mit bereits per bcrypt gehashten Passwörtern (10 Salting-Runden) – niemals im Klartext, auch nicht in diesem Demoskript.

    Kommentieren wir diesen Code:

    • Zeile 4: [@PrimaryGeneratedColumn()] – deklariert einen automatisch hochzählenden Primärschlüssel über das DBMS – das exakte Äquivalent von @Id + @GeneratedValue(strategy = GenerationType.AUTO) in JPA;
    • Zeile 7: [@VersionColumn()] – der [TypeORM]-eigene Mechanismus für das optimistische Sperren: [TypeORM] erhöht diese Spalte bei jeder Änderung automatisch und löst einen Fehler aus, wenn Sie versuchen, eine Entität zu speichern, deren Version nicht mehr mit der in der Datenbank übereinstimmt (jemand anderes hat sie in der Zwischenzeit geändert) – das exakte Äquivalent von @Version in JPA/Hibernate;
    • Zeile 3: [export abstract class AbstractEntity {] – diese Klasse ist nicht mit [@Entity] dekoriert: Sie entspricht für sich genommen keiner Tabelle. [TypeORM] bezeichnet diese Technik als „Concrete Table Inheritance“: Jede mit [@Entity] dekorierte Unterklasse erhält eine eigene Tabelle mit allen geerbten Spalten – das exakte Äquivalent von @MappedSuperclass in JPA.

      import { [Column], [Entity], [JoinColumn], [ManyToOne], [RelationId] } from 'typeorm';
  import { AbstractEntity } from './abstract.entity';
  import { Doctor } from './doctor.entity';

  @Entity({ name: 'slots' })
  export class Slot extends AbstractEntity {
    @Column({ name: 'start_hour' }) startHour: number;
    @Column({ name: 'start_minute' }) startMinute: number;
    @Column({ name: 'end_hour' }) endHour: number;
   @Column({ name: 'end_minute' }) endMinute: number;

   @ManyToOne(() => Doctor, (doctor) => doctor.slots)
   @JoinColumn({ name: 'doctor_id' })
   doctor: Doctor;

   @RelationId((slot: Slot) => slot.doctor)
   doctorId: number;
 }

    Zerlegen wir diesen Code:

    • Zeilen 7–10: [@Column({ name: 'start_hour' }) startHour: number; …] – die vier Zeitgrenzen des Terminzeitfensters (Beginn und Ende als Stunde/Minute), vier einfache ganze Zahlen, jeweils auf ihre Spalte in snake_case abgebildet (start_hour, start_minute, end_hour, end_minute);
    • Zeile 12: [@ManyToOne(() => Doctor, (doctor) => doctor.slots)] – mehrere Zeitfenster gehören zu demselben Arzt. Standardmäßig lädt [TypeORM] die Beziehung „doctor“ beim Lesen eines Zeitfensters nicht (standardmäßiges „Lazy“-Verhalten): Sie müssen sie ausdrücklich anfordern (Beziehungsoption: [...] in einer Abfrage) – genauso wie FetchType.LAZY auf der JPA-Seite ein explizites `left join fetch` in der JPQL-Abfrage erforderte, um den Arzt abzurufen;
    • Zeile 13: [@JoinColumn({ name: 'doctor_id' })] – legt den Namen der Fremdschlüsselspalte in der Tabelle [slots] fest;
    • Zeile 16: [@RelationId((slot: Slot) => slot.doctor)] – das exakte und idiomatische Äquivalent auf der [TypeORM]-Seite zum schreibgeschützten Feld idMedecin des ursprünglichen Projekts ([@Column](name = "id_medecin", insertable = false, updatable = false)): Es stellt den Wert des Fremdschlüssels direkt bereit, ohne die gesamte Entität [Doctor] laden zu müssen – nützlich, um schlanke JSON-Antworten zu erstellen (siehe unten, die Web-Schicht).

    Hinweis: Ein Feld [@RelationId] ist eine virtuelle Spalte, die nachträglich von [TypeORM] berechnet wird – es ist keine echte SQL-Spalte, die sich in einer WHERE-Klausel eines „Query Builders“ verwenden ließe (siehe unten, [SlotRepository]). Es dient ausschließlich dazu, den Wert des Fremdschlüssels auszulesen, sobald die Entität geladen ist.

    4.5. Die DAO-Schicht (src/repositories/)

    Die DAO-Schicht (Data Access Object) ist der einzige Teil des Projekts, der direkt mit TypeORM/MySQL kommuniziert – das Äquivalent der Spring-Data-Schnittstellen des ursprünglichen Projekts (Paket rdvmedecins.repositories).

    Der wichtigste Unterschied zwischen Spring Data und [TypeORM]: Bei Spring Data genügte es, eine Schnittstelle (extends CrudRepository<...>) zu deklarieren, um automatisch die grundlegenden Methoden (findAll, findOne, save, delete usw.) zu erhalten – Spring selbst erzeugte beim Start eine Klasse, die sie implementierte. Bei [TypeORM] gibt es keine automatische Erzeugung einer Implementierung aus einer Schnittstelle: Wir injizieren direkt das von [TypeORM] bereitgestellte generische Repository<Entity> (über [@InjectRepository]) und schreiben die Methoden, die wir anbieten möchten, selbst, indem wir auf den vordefinierten Methoden dieses Repository aufbauen oder für spezifischere Abfragen den Query Builder verwenden.

    4.8. Authentifizierung (src/auth/)

    Dieser Abschnitt dokumentiert die Ergänzung der tokenbasierten Authentifizierung (JWT) und der rollenbasierten Zugriffskontrolle (ADMIN/USER) an dieser Stelle des Kurses – das funktionale Pendant zur Spring-Security-Schicht des ursprünglichen Dokuments, neu geschrieben mit Standardwerkzeugen des [NestJS]-Ökosystems: [@nestjs/passport] und @nestjs/jwt.

    Zwei bewusste Unterschiede zum ursprünglichen Projekt, die hier ein für alle Mal festgehalten werden:

    1. JWT statt HTTP Basic. Das ursprüngliche Spring-Projekt sendete bei jeder Anfrage den Header Authorization: Basic <login:password in Base64>: Das Passwort (kodiert, nicht verschlüsselt) wurde also bei jedem Aufruf über das Netzwerk übertragen. Diese Portierung verwendet stattdessen ein Token: JWT (JSON Web Token). Das Passwort wird nur einmal beim Login übermittelt (POST /login); der Server liefert dann ein signiertes Token zurück, das der Client anschließend in jede weitere Anfrage einfügt (Header Authorization: Bearer <token>). Dies ist die heute übliche Praxis für diese Art von API, wie bereits im Fazit des vorherigen Kapitels erwähnt.
    2. Eine Rolle pro Benutzer, eine einzige Datenbankspalte statt der Many-to-many-Beziehung (users/roles/users_roles) im ursprünglichen Projekt – siehe user.entity.ts weiter oben.

    Ein architektonischer Punkt, den Sie vor dem Lesen des folgenden Codes verstehen sollten: Wenn ein Guard eine Anfrage ablehnt (401 Unauthorized, 403 Forbidden), durchläuft die Antwort niemals den üblichen [ServerResponse]<T>-Umschlag ({ status, data }): [NestJS] antwortet direkt in seinem nativen JSON-Format { statusCode, message, error }. Das ist eine bewusste Entscheidung: Sicherheitsfehler werden vor dem Eintritt in den Controller (durch einen Guard) behandelt, während [ServerResponse]<T> vom Controller für fachliche Fehler erzeugt wird (Ressource nicht gefunden, ungültiges Datum usw.). Der [Vue.js]-Client muss daher zwischen diesen beiden Arten von Fehlerantworten unterscheiden (siehe das folgende Kapitel, auth.interceptor.ts).

     logging: process.env.NODE_ENV !== 'production',
   };
 }

    Kommentieren wir diesen Code:

    • Zeile 8: [export function getDatabaseConfig(): TypeOrmModuleOptions {] — entspricht der Klasse DomainAndPersitenceConfig des ursprünglichen Spring-Projekts, die einen DataSource definierte (Block @Bean). Hier gibt es keine Klasse: nur eine einfache Funktion, die ein Konfigurationsobjekt zurückgibt, das aus den Umgebungsvariablen gelesen wird (die Datei .env; siehe unten);
    • Zeile 16: [entities: [Doctor, Client, Slot, Appointment, User],] — die Liste der Entitäten, die [TypeORM] verwalten muss – entspricht dem automatischen „Scan“ der [@Entity]-Klassen durch Spring Boot. [User] wurde mit der Einführung der Authentifizierung zu dieser Liste hinzugefügt: Würde man sie weglassen, käme es beim Start zu einem Fehler „no metadata found for [User]“;
    • Zeile 17: [synchronize: false,] — in diesem Kurs immer vorhanden: Wäre `synchronize` auf `true` gesetzt, [TypeORM] würde das Datenbankschema automatisch anhand der Entitäten ändern – nützlich für einen Wegwerf-Prototyp, aber gefährlich, sobald echte Daten im Spiel sind (Gefahr von Datenverlust). Die Kontrolle über das Schema behalten wir über das Skript [database/dbrdvmedecins.sql];
    • Zeile 18: [logging: process.env.NODE_ENV !== ‘production’,] — zeigt die von [TypeORM] erzeugten SQL-Abfragen in der Konsole an, genau wie die Hibernate-Logs im ursprünglichen Spring-Projekt.

    • Zeile 1: [import ‘dotenv/config’;] — muss der allererste Import in dieser Datei sein: Sein einziger Zweck ist es, die Datei .env zu lesen und ihren Inhalt nach process.env zu kopieren, bevor irgendetwas anderes ausgewertet wird – insbesondere bevor app.module.ts (in Zeile 5 importiert) seinerseits database.config.ts und auth/auth.module.ts lädt, die beide process.env lesen, sobald sie geladen werden (DB_HOST, JWT_SECRET …). Ohne diese Zeile an genau dieser Stelle wäre eine auf der Festplatte vorhandene .env-Datei nutzlos: Die Variablen würden in process.env schlicht nicht existieren, wenn diese Module sie brauchen;

    • Zeile 9: [app.enableCors();] — erlaubt dem [Vue.js]-Client (der auf einem anderen Port läuft), diesen Server aufzurufen. Ohne dies würde der Browser die Anfragen aus Sicherheitsgründen blockieren;

B. String "3" → Zahl 3), und `whitelist: true` entfernt aus den empfangenen Daten die Felder, die im `DTO` nicht deklariert sind;
    • Zeile 16: [const port = process.env.PORT ? parseInt(process.env.PORT, 10) : 8080;] — der Standardport 8080 ist derselbe wie beim ursprünglichen Spring-Boot-Server.

    4.10. Durchgängige Überprüfung

    Dieser Schritt wurde anhand von etwa zehn curl-Szenarien gegen eine Testkopie des Servers überprüft (In-Memory-Datenbank, vorab befüllt mit den beiden Konten admin/admin und user/user):

    • POST /login mit den korrekten Zugangsdaten liefert korrekt { "status": 0, "data": { "accessToken": "...", "login": "admin", "name": "Administrator", "role": "ADMIN" } } zurück;
    • POST /login mit einem falschen Passwort liefert 401 Unauthorized (natives JSON-Format von [NestJS], nicht der [ServerResponse]<T>-Umschlag);
    • GET /getAllDoctors ohne Header Authorization liefert eine Antwort 401 Unauthorized;
    • GET /getAllDoctors mit einem gültigen JWT-Token (admin oder user) liefert wie üblich die Liste der Ärzte im gewohnten [ServerResponse]<T>-Umschlag;
    • POST /addAppointment mit dem Token von admin reserviert normal einen freien Zeitslot;
    • POST /addAppointment mit dem Token von user liefert einen Fehler 403 Forbidden, mit der Meldung, dass die Rolle [USER] diese Aktion nicht erlaubt (erforderliche Rolle: ADMIN);
    • POST /deleteAppointment verhält sich je nach Rolle des übergebenen Tokens symmetrisch zu /addAppointment.
